The Cloud Network Flow Problem

The optimization problem tackled in this work is the Cloud Network Flow problem — the Cloud Service Distribution Problem (CSDP) introduced by Jaime Llorca, Antonia M. Tulino and collaborators. It models service delivery over a distributed cloud network: an edge/fog/cloud substrate whose nodes are equipped with both communication and computation resources, interconnected by capacitated transport links. Although the code package is named vne/ for historical reasons, the problem it solves is not generic Virtual Network Embedding (VNE) — it is the richer cloud-network-flow model in which flows are simultaneously routed over links and processed at compute nodes.

Attribution. The Cloud Service Distribution / Cloud Network Flow model is due to Llorca, Tulino et al. (Barceló, Llorca & Tulino, The Cloud Service Distribution Problem in Distributed Cloud Networks, IEEE ICC 2015; Feng, Llorca, Tulino & Molisch, Optimal Dynamic Cloud Network Control, IEEE/ACM Transactions on Networking, 2018). The contribution of this repository is the neural sequence-decoding formulation of that problem and the self-improving-learning program built on it — not the problem model itself.

Problem definition

A cloud network is a directed graph of nodes carrying transport (link bandwidth) and compute (node processing) capacity. Services are delivered as generalized multi-commodity flows that must be both transported over communication links and processed at compute nodes. Concretely, the model has the following ingredients:

  • Cloud network (substrate) G(V, E). A directed graph. The node set V = C ∪ P contains two node types: communication nodes C and computation nodes P. The edge set contains two link types: communication links (C → C) carrying bandwidth, and computation links (C ↔ P) carrying processing capacity. Each communication node is attached to at most one co-located computation node.
  • Services as service-function chains R(M, K). Each request is a chain of virtual functions that a flow must traverse in order. Its node set M = S ∪ F ∪ D comprises a single source S, a sequence of processing functions F, and a single destination D. Its links are of three types: a source link (S → Fi), processing links (Fi → Fj), and a destination link (Fz → D). The flow enters at the source, is processed at successive functions hosted on compute nodes, and is delivered to its destination.
  • Link-level encoding. Crucially, in this formulation nodes carry no attributes: all capacity and demand information lives at the link level. Communication links carry bandwidth BW(Ci → Cj); computation links carry paired capacity CAP(Pi → Ci) = CAP(Ci → Pi). Because a computation resource is represented by a bidirectional link pair, allocating on one direction deducts from both directions simultaneously.

Cloud network flow, constraints, and objective

A feasible solution places every service chain onto the substrate and routes each of its inter-function flows so that: (i) each source/destination link is placed on a computation link (the function is hosted on a compute node), (ii) each processing link is routed along a directed communication path that respects link direction exactly, and (iii) all residual bandwidths and capacities remain non-negative under generalized flow conservation — the output of one stage feeds the next. The objective is to minimize total communication (transport) cost + computation cost, the classic minimum-cost cloud-network-flow objective. Because all constraints are linear, the problem is solvable exactly as an ILP (labelling here uses HiGHS or Gurobi), which provides the optimal reference cost F* for training and evaluation.

Why it is a hard combinatorial problem — and why generic VNE encodings fail

The Cloud Network Flow problem is combinatorially hard because it couples two decisions that are usually studied separately: placement (which compute node hosts each function) and routing (which substrate path carries each inter-function flow), under shared, capacitated resources. Placement and routing interact — where a function is hosted constrains which paths are feasible for the adjacent flows, and every reservation shrinks the residual capacities available to later requests in the same instance.

The standard VNE tuple encoding — embed a virtual graph by choosing a one-to-one node placement plus edge routings, maximizing revenue over cost — does not translate into a clean learning target here. As the formulation notes, if we try to emit a solution tuple a = (a1, a2, …) under the generic encoding, two problems arise:

  • Massive, redundant search space. Many equivalent solutions exist under different tuple orderings, so the decoder wastes capacity distinguishing permutations that denote the same embedding.
  • Heterogeneous action semantics. Some tuple entries would refer to nodes and others to edges, mixing two incompatible action types in a single sequence — there is no uniform, well-typed "next decision" for a sequence model to predict.

The extended, link-level encoding as a sequence-decoding task

The extended encoding resolves both issues by moving all information to the link level and unifying the action type. Because source/destination links map to computation links and processing links map to communication paths, every decision has the same shape: it selects a feasible substrate path for the next inter-function flow of the current service chain. This yields a clean sequence-decoding task:

  • One decision = pick a feasible substrate path for the next inter-function flow of the chain being placed.
  • Decoding a chain in order (source link → processing links → destination link) naturally realizes both the placement and the routing without a separate node-selection action type.
  • A full trajectory places and routes every chain in the instance, with residual capacities updated after each committed path — exactly the setting TaSaR's step-and-reconsider decoder is designed for.

Concretely (from the worked example in the formulation): given a chain S —3→ F1 —4→ F2 —5→ D, one feasible allocation places the source link on computation link C1 → P1 (reserving 3 units from both paired directions), routes the processing link along the directed communication path C1 → C2 → C4 (reserving 4 units per hop), and places the destination link on C4 → P4 (reserving 5 units from both directions). Each of these is a single "pick a feasible substrate path" decision in the decoded sequence.

Training objective and default scale

Training uses a lexicographic objective: feasibility first (embed all requests within capacity), then cost (minimize transport + compute cost). This ordering makes feasibility a primary, first-class metric rather than an afterthought — unlike the routing/scheduling domains of the original TaSaR paper, where every trajectory is feasible by construction, here feasibility is a genuine outcome to be maximized. Best-model selection follows the same rule (feasibility-first, then gap).

The default instance scale is:

ParameterDefault range
Communication nodes per substrate60–80
Service requests per instance10–20
Functions per service chain2–5
Feasibility is the headline metric. Because the training objective is lexicographic (feasibility > cost) and instances are not feasible by construction, feasibility% is the primary quantity reported throughout. Optimality gaps are computed against the ILP optimum F* and, in the results sections, are averaged over the set of instances feasible under every compared method so they remain orderable.

Method: TaSaR, Self-Improving Learning, and Architectures

The method has three interlocking parts. A policy network reads the current placement-and-routing state of a service chain and scores each feasible substrate path for the next inter-function flow. A TaSaR decoder turns that greedy-per-step policy into a strong anytime search that produces high-quality full solutions by repeatedly committing a few steps and reconsidering alternatives. A Self-Improving Learning (SIL) loop closes the circle: the decoder generates better-than-greedy solutions on fresh instances, and those solutions become the next epoch's training labels, so the policy bootstraps itself upward without any new human labels. This section explains each part, why it is designed the way it is, and the engineering fixes that made the whole program run on a single GPU.

The sequence-decoding formulation

To use a sequence decoder at all, Cloud Network Flow is cast as a Markov decision process over placement-and-routing decisions. One decision = pick a feasible substrate path for the next inter-function flow of the current service chain. Consuming decisions in order places and routes every function of every chain; a completed trajectory is a full embedding. Let l denote the number of such inter-function-flow (virtual-link) decisions in an instance — this is the trajectory length and the key quantity in the compute-budget accounting below. The objective a trajectory is scored on is lexicographic: feasibility first (embed all requests within link-bandwidth and node-compute capacity), then cost (transport + compute). Because the framework maximizes an outcome, the policy's leaf-evaluation returns feasibility-first-then-negative-cost, mirroring how the routing baselines return negative tour length.

(a) The TaSaR decoder — beam width k, step size s, constant Top-p

TaSaR (Take a Step and Reconsider) is implemented in core/incremental_sbs.py::IncrementalSBS.perform_tasar. It sits on top of Stochastic Beam Search (SBS) — sampling without replacement from the policy via the Gumbel-top-k trick over a trajectory trie. The TaSaR wrapper adds the "step and reconsider" control loop with two knobs plus a truncation parameter:

  • Beam width k (beam_width) — how many alternative continuations SBS samples without replacement each time it reconsiders. Larger k considers more distinct candidate sequences before committing.
  • Step size s (replan_steps, the paper's step size) — how many actions the decoder commits to the current best solution before it stops and re-samples alternatives from the new position.
  • Constant Top-p (min_nucleus_top_p, the paper's p_min) — nucleus truncation applied on every SBS round. Crucially it is held constant across rounds, unlike the original gumbeldore schedule that anneals p up to 1.

The control loop (verified in perform_tasar) is: from the current root, run one round of SBS with beam width k under constant Top-p to get a batch of candidate leaves; keep the best leaf seen so far (by the maximize-objective leaf-evaluation); read off the first action on the path to that best leaf and commit it — shift the root one node down that action, mark the freshly sampled mass as consumed, and drop the trie above the new root. Do this for s consecutive commits (following the same best solution), then run a fresh SBS round from the advanced root to reconsider. Repeat until the root becomes a leaf, i.e. the whole chain set is embedded. The first round may optionally be deterministic beam search (perform_first_round_deterministic) to "get the policy's exploitation out of the system" before sampling begins.

The intuition for s is the method's core trade-off between lookahead frequency and cost:

  • s = 1 is MCTS-like: the decoder re-searches after every single committed action, so it maximally reconsiders — the most lookahead, and (see the budget formula) the most compute.
  • s = l reduces to plain SBS: it searches once from the root, commits the entire best trajectory, and never reconsiders — one shot, cheapest.

Everything in between trades reconsideration frequency against compute. The compute budget is measured in node transitions (paper Eq. 3), not wall-clock, so it is hardware-independent:

Smaller s means MORE compute, not less. Because t = ⌈l/s⌉ grows as s shrinks, a small step size triggers many reconsider rounds and inflates g_TaSaR. This is the opposite of the naive intuition that "fewer committed steps = cheaper." In the results, (k=16, s=4) costs ⟨g⟩=3226 node-transitions vs. ⟨g⟩=594 for beam search k=16 — the extra budget is exactly what buys the jump to 100% feasibility.

(b) The Self-Improving Learning (SIL) loop

SIL is the training regime that makes a decode-time improvement compound into a better policy. It runs through the shared core/train.py::main_train_cycle with learning_type = "gumbeldore" and search_type = "tasar", seeded from a supervised checkpoint. Each epoch:

  1. Seed: start from a supervised model (Phase 1) that has learned to imitate ILP-optimal embeddings — good enough to bootstrap, far from solved (BQ SL greedy is only 27.7% feasible).
  2. Generate: sample fresh random instances (substrate + service requests).
  3. TaSaR-decode: run perform_tasar on each instance to produce a solution better than the policy's own greedy rollout — the decoder acts as a policy-improvement operator.
  4. Train: run one supervised epoch on those self-generated (instance, TaSaR-solution) pairs, teaching the network to imitate its own improved search output.

Repeat. Because the decoded solutions are consistently better than greedy, each epoch shifts the policy toward the decoder's behaviour, which in turn makes the next epoch's decoding start from a stronger base — a self-reinforcing loop that needs no ground-truth labels after the seed. Ray distributes the generation step across workers (one per device entry), pickles the solutions, and reuses them as the epoch's dataset. The best checkpoint is selected feasibility-first (see enabler 2).

(c) BQ vs. LEHD architectures

Both networks solve the same problem: map a state (substrate + service chains + the current inter-function flow) and its list of feasible candidate substrate paths to one logit per candidate, i.e. a distribution over the next path to commit. They differ in how they mix information.

BQ — single unified transformer (vne/bq_network.py)

The BQ (Bisimulation Quotienting) network embeds four token types — [nodes | edges | virtuals | candidates] — each with a learned token_type_embedding marker, concatenates them into one flat sequence, and runs a single transformer stack (default 9 ReZero blocks, dim 128) with all-to-all attention over the whole sequence. There is no encoder/decoder split and no cross-attention: candidate tokens attend directly to every node, edge, virtual, and other candidate. After the stack, the candidate positions are sliced out and a single linear layer projects each to its logit. This is the paper's BQ-NCO recipe (Drakulic et al.) applied unchanged to Cloud Network Flow.

LEHD — encoder/decoder (vne/network.py)

The LEHD (Light Encoder, Heavy Decoder) network splits the computation. A light encoder (default 1 layer) processes [nodes | edges | virtuals] into contextual token embeddings. A heavier decoder (default 3 layers) then attends over a short sequence [global_context, current_virtual, candidate_1 … candidate_C], where: global_context is the mean-pooled encoder output, current_virtual is the encoded token of the flow being placed, and each candidate token is built by pooling the encoder embeddings of the substrate nodes and edges along that candidate path and adding the candidate's own features. The decoder output at each candidate position is projected to its logit. So LEHD explicitly grounds each candidate in the concrete substrate resources its path traverses, then reasons over the small candidate set in the decoder; BQ instead lets a single deep stack discover those interactions via full attention.

Both forwards are batched with padding + key-padding masks and are exactly equivalent to the per-state forward because the transformers carry no positional encoding (pure set attention) — this is what makes generation fast enough to be practical (enabler 1). Architecture is selected via config.architecture (bq / lehd).

(d) The three engineering enablers

1. Behaviour-preserving 8.6× generation speedup

TaSaR data generation was the bottleneck: SIL regenerates a dataset every epoch, and each instance requires many policy forward passes across many reconsider rounds. Batching the network forwards (single host→device copy, padded set-attention as above) cut per-instance generation from 56 s to 6.5 s on a 70-node instance — an 8.6× speedup that is behaviour-preserving (identical logits, no retrain needed). Without it the multi-epoch SIL program, the multi-beam sweep, and the generalization study would not have been tractable on a single GPU. A profiling/equivalence harness lives at scripts/vne_hotpath_harness.py.

2. Lexicographic best-model-selection fix

Because feasibility is the primary objective, model selection must rank feasibility before gap — a lower-gap-but-less-feasible epoch is worse, not better. The fix selects best_model.pt by the lexicographic score (1 − feas)·1000 + gap, so any feasibility gain dominates any gap change. A correctness rule accompanies it: every budget row (greedy / BS / TaSaR) for a group must be evaluated on the same selected checkpoint, or the comparison is invalid.

3. The Top-p correctness point (p = 1.0 is the baseline, not TaSaR)

TaSaR requires Top-p < 1. Setting min_nucleus_top_p = 1.0 disables nucleus truncation, which turns the decoder into un-truncated sampling-without-replacement SBS — this is exactly the Gumbeldore / GD-SIL baseline, not TaSaR. The genuine "Ours" runs use p = 0.9 (env VNE_MIN_TOP_P). Labelling a p = 1.0 run as "TaSaR" would silently compare the baseline against itself. This is not a cosmetic distinction: the LEHD p = 1.0 (GD SIL) run diverged, collapsing from the seed's 58% feasibility to 5–19% across all 10 epochs, while both LEHD p = 0.9 and BQ p = 1.0 stayed stable — direct evidence that TaSaR's Top-p truncation also aids training stability.

Why the headline numbers are not a regression

A recurring trap in reading the SIL results is the feasible-pool-composition confound. When SIL lifts feasibility (e.g. seed 36.8% → SIL ~60%), roughly two dozen percentage points of harder instances newly enter the feasible pool. Since gap% is averaged over the set of instances feasible under the compared methods, adding harder instances to that set can raise the mean gap even though every individual instance is solved at least as well. That is why gap% is always reported over F* — the fixed set of instances feasible under every compared method, giving a common, orderable denominator. Under the lexicographic objective, Feas% (over the full test set) is the headline metric and Gap%(F*) is the conservative secondary; a feasibility gain accompanied by a slightly higher F*-gap is an improvement, not a regression.

Experimental Setup, Metrics & Rigor

This section documents exactly how the Cloud Network Flow (VNE) experiments were run and, more importantly, why the reporting is structured the way it is. The measurement design is deliberately conservative: because feasibility is a first-class outcome here (unlike the paper's routing and scheduling domains, where every trajectory is feasible by construction), several reporting conventions that are trivial in the original TaSaR setting become subtle and must be handled with care. We spell out the datasets and labelling, the metrics and their pitfalls, the compute-fair budget accounting, and the mapping of our tables onto the paper's Table 1 structure.

(a) Datasets, ILP labelling, test sets, and hardware

Substrate scale and instances. Training and the in-distribution test set use substrates of 60–80 communication nodes with 10–20 virtual requests per instance (line-topology service chains, embed-all, min-cost objective). Each node carries both compute and communication capacity, and each request is a chain of virtual functions that must be jointly placed and routed as a min-cost (mixed-cast) flow. Instances are produced by make_instance/generate_instance; the generator resamples until a feasibility-possible instance is obtained, so a substrate admitting no valid embedding is never scored.

ILP labelling (HiGHS / Gurobi). Supervised seeds and gap references come from solving each instance's mixed-cast min-cost flow as an exact integer program. Two backends are wired through PuLP: HiGHS (open, no license) is the default reference solver—the analogue of Concorde/HGS in the paper—and Gurobi (academic license) is used for the larger generalization labels where speed matters. In-distribution (1×, 60–80-node) labels are solved to exact optimality (mip_gap = 0). The larger generalization labels (1.35×, 90–110 nodes) are time-bounded near-optimal (bounded Gurobi, labels ≤ 5% loose) because exact labelling explodes with size on a single machine (≈10 s @ 80n, ≈21 s @ 100n; at ≥120 nodes the bounded solves time out, the generator resamples, and cost climbs to ≈28 min/instance). This is why the gap study has a hard ceiling at 90–110 nodes.

Test sets. Evaluation is on a 2k-instance in-distribution pool (vne_test_dataset_2k.pickle, 60–80 nodes), with the Phase 2/3 result tables scored on a fixed N = 256 evaluation subset drawn from it. Generalization uses separate sets: small ILP-labelled sets at 1.35× (90–110 nodes, N = 16) for the gap table, and unlabelled substrates up to 320 nodes (≈4.6× the trained scale) for the label-free feasibility-vs-scale sweep (N = 16 per scale).

Hardware. All timings are single-worker on one RTX 5060 (8 GB). This is deliberately weaker than the paper's 4×RTX-3090 setup, so our wall-clock and per-instance times are not comparable to the paper's totals; they are reported only for internal cost–quality tradeoffs on our hardware. The 8 GB budget also forces the candidate-path cap (500) and small training batch sizes.

(b) Metrics: Feasibility%, Gap%, and the feasible-pool confound

Feasibility% (headline). Feas% is the fraction of the full test set (N = 256) that a method embeds completely. It has no analogue in the paper's Table 1: routing/JSSP trajectories are always feasible, so the paper only ever reports a gap. In Cloud Network Flow, capacity and chaining constraints make an embedding genuinely findable or not, and the training objective is lexicographic (feasibility first, then cost). Feasibility is therefore the primary ranking metric, and Feas% (over the full N) is the robust, label-independent number to trust.

Gap% and why it must be averaged over F*. Gap% is the mean relative gap to the HiGHS ILP optimum. The danger is that different methods leave different subsets of instances infeasible, and a gap computed only over “instances this method happened to solve” is non-orderable across methods—a stronger method that additionally solves several hard, high-cost instances can show a worse average gap purely because its denominator is harder. To make gaps orderable we fix the denominator: gap is averaged over F* = the intersection of instances feasible under every compared method (instances with ilp_obj == 0 excluded and counted separately). A fixed F* means the same instances are compared row to row, so ranking on Gap%(F*) is meaningful.

Rigor point 1 — the feasible-pool-composition confound (why 37%→60% feas with gap 2.08→2.84 is NOT a regression). When self-improvement lifts feasibility from ≈37% to ≈60%, roughly 24 pp of previously-infeasible, harder instances enter the feasible pool. Those newcomers have higher optimal cost and larger residual gaps, so the average gap over the (now different, harder) feasible pool can rise even though no individual solution got worse. The seed and the SIL model are simply averaging over different instance sets. This is a composition artifact, not a quality regression—which is precisely why Gap% is only ever compared on a fixed F*, and why Feas% is the headline. (Concretely: with the weak BQ SL greedy row at 27.7% feas shrinking the 6-row F* to an easy 39-instance subset, we also report an auxiliary gap over the stronger-rows F*=95 to give a fuller picture.)

(c) Compute-fair budget g(k,s): node transitions, and “smaller s ⇒ more compute”

To compare methods at matched search effort we count node transitions (the paper's Eq. 3), not wall-clock. For beam width k, step size s, and l = number of virtual-link assignment decisions per instance (with t = ⌈l/s⌉ replan rounds):

The counter-intuitive part: a smaller step size s means more compute, not less. Small s commits to fewer actions before re-planning, so it triggers more replan rounds t = ⌈l/s⌉, each of which re-searches; the budget grows with t. This is the opposite of a naive k·s intuition and is why, in the result tables, TaSaR(k=8, s=4) at ⟨g⟩≈1613 and TaSaR(k=16, s=4) at ⟨g⟩≈3226 dominate the ⟨g⟩=37 greedy and ⟨g⟩=594 beam-16 rows. When we claim “TaSaR beats beam search at matched budget,” matched means matched g, not matched wall-clock.

Rigor point 2 — feasibility-first bolding and cross-scale gap caution. Under the lexicographic objective, Feas% is the primary key: we do not bold a lower Gap% across rows that have different Feas% (a gap on a different feasible subset is not a like-for-like win); Gap% is only bolded on a common F*. Separately, gap is not comparable across substrate scales: 1× labels are exact (mip_gap 0) while 1.35× labels are ≤5% loose, so an apparent gap improvement at larger scale is partly a label-tightness artifact. At the larger scales, Feasibility% is the clean, label-independent headline and gap is reported only where exact labels exist.

Enabling infrastructure behind these experiments: an 8.6× faster, behaviour-preserving generation path (56 s→6.5 s per 70-node instance), a lexicographic best-model selection fix (best_model.pt chosen by (1−feas)·1000 + gap, so every greedy/BS/TaSaR row in a group uses the same checkpoint), and Gurobi wired through PuLP for the larger-scale labelling.

Results I: Self-Improving Learning (Phases 1–2)

This section reports the core Self-Improving Learning (SIL) result: starting from a supervised seed and iteratively regenerating training data with TaSaR decoding produces a policy that, once combined with inference-compute scaling, solves the in-distribution test set — 100% feasibility and a 0.00% optimality gap on the BQ architecture. We evaluate both policy architectures (BQ, a single unified transformer over nodes/edges/virtuals/candidates; LEHD, an encoder–decoder) on N = 256 held-out test instances of the Cloud Network Flow problem, against the HiGHS ILP optimum.

Why TaSaR, and why these numbers

(a) SIL beats the supervised seed at every budget

The supervised checkpoints are weak on their own — SL greedy feasibility is only 27.7% (BQ) and 58.2% (LEHD). SIL uses these seeds merely as a starting point: each epoch it generates fresh instances, decodes strong solutions with TaSaR, and trains on them. This self-generated curriculum raises feasibility across the board. Even the cheapest SIL greedy decode (BQ: 53.1%, LEHD: 55.5%) dominates or roughly matches the seed, and every higher inference budget improves further, monotonically.

(b) Inference-compute scaling solves the in-distribution set

The ⟨g⟩ column makes the scaling law explicit: budget grows from 37 node transitions (greedy) to 3226 at (k=16, s=4), an ~87× increase, and feasibility/gap improve monotonically the whole way. For BQ this converges to feas 100.0% / gap 0.00% — the search recovers the exact ILP optimum on every test instance. This is the central claim of applying TaSaR here: the policy need not be perfect in a single greedy pass, because bounded-depth reconsideration at inference time closes the remaining quality and feasibility gap.

(c) GD-SIL vs Ours(TaSaR), and the greedy-feasibility inversion

The distinction is precise and load-bearing: TaSaR requires Top-p < 1. Setting min_nucleus_top_p = 1.0 gives un-truncated WOR-SBS, which is exactly the Gumbeldore / GD-SIL baseline — not TaSaR. The genuine "Ours" runs use p = 0.9. This explains an apparent paradox in the BQ table: the p=1.0 GD-SIL model has higher greedy feasibility (62.9%) than the p=0.9 Ours model (53.1%). The two models were trained under different sampling regimes, so their greedy behavior differs; but the point of TaSaR is inference under truncated reconsideration, where Ours dominates — scaling to 100% feasibility and 0.00% gap. Greedy feasibility of the p=0.9 checkpoint is not the figure of merit; its TaSaR-decoded performance is.

(d) The feasible-pool confound — do not misread the gap

Gap%(F*) is averaged over a fixed, shared denominator; feasibility% is the primary ranking. Because F* is the set of instances feasible under every compared row, a weak baseline (BQ SL greedy, 27.7% feas) shrinks F* to just 39/256 easy instances. When SIL lifts feasibility, roughly 24pp of harder instances enter the feasible pool, which can make the mean gap tick up even though the model strictly improved — this is the feasible-pool-composition confound, not a regression. The completed feas 37%→60% with gap 2.08→2.84 pattern is exactly this trap: the two gaps are computed over different instance subsets. Treat Feas% (over the full N) as the robust metric and Gap%(F*) as conservative. The auxiliary F*=95 denominator (excluding the weak SL baseline) gives a cleaner view: gap 3.13 (greedy) → 2.01 (bs k=16) → 0.33 (k=8 s=4) → 0.07 (k=16 s=4), strictly monotone and converging to ~optimal.

Results II: Inference Scaling with Beam Width (Phase 3)

Phase 2 established that self-improving learning with TaSaR (Top-p = 0.9, the genuine “Ours” setting) yields strong Cloud Network Flow policies. A natural next question is whether these policies actually benefit from wider search at inference time, or whether a single greedy rollout already extracts everything the network knows. Phase 3 answers this by taking the two Phase 2 “Ours” models — the unified BQ transformer and the LEHD encoder/decoder — and evaluating each under deterministic beam search at beam widths 1, 4, 8, 16, 32, and 64. No new models are trained and no supervised baselines are introduced; this is a pure inference-scaling study on N = 256 held-out test instances.

The central mechanism being probed is the “reconsider” step: SBS/TaSaR only helps if the policy’s alternative continuations — the ones a wider beam retains rather than discarding — are genuinely useful. If beam-1 (greedy) were already as good as beam-64, the diverse alternatives would be noise and the entire method would collapse to a deterministic decoder. Showing that quality keeps improving with beam width is therefore direct evidence that the search component is doing real work on this problem class.

How to read the numbers. Feasibility% is computed over the full N = 256 test set. Gap% is averaged over each model’s all-beam-feasible set — the instances that are feasible at every beam width for that model (BQ: 116 instances; LEHD: 141). Fixing the denominator this way is what makes the gap-vs-beam curve monotonically orderable: every point is measured on the same instance subset, so improvements reflect solution quality rather than a shifting feasible pool. The two models’ gap columns are not directly comparable to each other, because each is averaged over its own feasible subset.

Interpretation

(a) Both feasibility and gap improve monotonically with beam width. For BQ, feasibility climbs from 53.1% at beam-1 to 99.2% at beam-64, while gap falls from 3.227% to 1.751%. For LEHD the pattern is even sharper: feasibility rises from 55.5% to 99.6% and gap drops from 3.782% all the way to 0.553%. Because beam-1 is decisively worse than beam-64 on both axes, the diverse alternatives that SBS/TaSaR retains are demonstrably useful — the network’s second, third, and later choices frequently lead to feasible, lower-cost embeddings that greedy decoding would never reach. This is exactly the behaviour the “take a step and reconsider” mechanism is designed to exploit, and it confirms that the reconsider step transfers to the Cloud Network Flow domain rather than being an artifact of the paper’s routing/scheduling problems.

(b) LEHD scales better than BQ on gap. At beam-64 LEHD reaches a 0.553% gap versus BQ’s 1.751%, and its gap curve decreases cleanly and monotonically across every width. BQ’s gap, by contrast, is essentially flat for small beams (3.227 → 3.298 → 3.149 across beams 1–8) before dropping once the beam is wide enough to escape the greedy basin. The LEHD encoder/decoder factorization appears to produce a better-calibrated distribution over continuations, so additional beam capacity converts more directly into solution-quality gains.

(c) The key comparison — TaSaR still beats deterministic beam-64 at matched budget. This is the paper’s central claim, and it holds for Cloud Network Flow. The Phase 2 TaSaR(k=16, s=4) configuration reached gaps of roughly 0.07–0.32%, which is below every deterministic beam-64 gap reported here (BQ 1.751%, LEHD 0.553%). TaSaR’s sample-and-reconsider strategy therefore extracts more quality per unit of compute than simply widening a deterministic beam — consistent with the compute-budget accounting g(k,s) in node transitions, where TaSaR spends its budget on re-planning from committed partial solutions rather than on a uniformly wide frontier.

(d) Cost–quality Pareto and the fixed-denominator caveat. Wall-clock cost scales approximately linearly with beam width — ms/inst roughly doubles at each doubling of the beam — giving a clean cost–quality Pareto frontier that a practitioner can dial along. As a reminder for correct reading of the tables: each model’s gap is averaged over its own all-beam-feasible set (BQ 116, LEHD 141 instances), so the gap columns index solution quality on a fixed subset per model and should not be cross-read between BQ and LEHD as an absolute ranking.

Results III: Generalization to Larger Networks (Phase 4)

The Phase 2 models were trained exclusively on substrates of 60–80 nodes. A natural and important question for any learned combinatorial solver is whether it degrades gracefully — or catastrophically — when confronted with instances larger than anything it saw during training. Phase 4 answers this evaluation-only, with no retraining: we take the identical "Ours" checkpoints (BQ and LEHD, TaSaR decoding at Top-p = 0.9) and evaluate them on progressively larger networks. Where an optimal reference is needed for the gap metric, labels are produced with Gurobi under an academic license.

Two complementary experiments are reported. The first (Table 4) is a fully-labelled generalization study out to 1.35× the trained size, giving both feasibility and optimality gap. The second sheds the labelling requirement to push feasibility all the way to ~4.6× the trained size — infeasible to label, but still answerable because feasibility needs no optimum.

The models generalize to 1.35×-larger substrates with strong feasibility under search. Greedy feasibility drops as expected on harder out-of-distribution instances (≈53–56% at 1× down to 43.8% at 1.35× for both models), but beam-16 recovers almost all of it: BQ climbs back to 87.5% and LEHD to a perfect 100.0%. In other words, the "reconsider" mechanism — sampling and re-evaluating alternatives rather than committing to a single greedy chain — is precisely what transfers to larger-than-trained sizes. LEHD generalizes especially well, reaching full feasibility at 1.35× under bs16.

Gap is not comparable across scales. The 1× labels are exact (Gurobi mip_gap 0), whereas the 1.35× labels are ≤5% loose — the solver was time-bounded to keep labelling tractable. Consequently the apparent gap improvement at 1.35× (e.g. BQ 2.36 → 0.63, LEHD 1.33 → 0.18) is partly a label-tightness artifact, not a genuine quality gain: a looser reference optimum makes the model's cost look closer to it. Feasibility% is the clean, label-independent metric and should be read as the headline here.

Additional caveats: N = 16 at 1.35× makes those estimates noisy (each instance moves feasibility% by 6.25 points), and 1.35× is itself a modest extrapolation. For a much larger-scale view, see the feasibility-vs-scale study below.

Why gap stops at 1.35× but feasibility reaches 4.6×

The asymmetry between the two studies is not arbitrary — it follows directly from what each metric requires. Gap is the only labelling-bound part of the evaluation. It needs an optimum reference from Gurobi, and ILP labelling cost explodes with substrate size on a single machine: roughly 10 s per instance at 80 nodes, ~21 s at 100 nodes, and at ≥120 nodes the bounded solves time out, triggering generate_instance to resample — pushing effective labelling to ~28 minutes per instance. The 90–110-node band is therefore the tractable ceiling for gap on the available hardware. Feasibility, needing no solver, has no such wall.

Net conclusion: gap is reported only up to 1.35× (Table 4), while feasibility extends to ~4.6× (the scale table). Recovering gap at larger scales would require many parallel Gurobi licences — notably not the GPU cluster used for training and inference, which has no Gurobi installed.

7. Synthesis, Limitations & Future Work

7.1 What the four phases add up to

Taken together, the experimental program establishes a single coherent story: TaSaR-style self-improved learning transfers cleanly from the paper's routing/scheduling domains to the Cloud Network Flow problem, and the mechanism that carries it is search, not just the learned greedy policy. The narrative runs in three movements, one per experimental phase after the supervised seed.

(1) Self-Improving Learning works (Phase 2). Seeded from a purely supervised policy and then trained only on its own TaSaR-decoded solutions, the policy learns to embed substantially more instances. On the in-distribution N=256 test set, the BQ Ours model climbs from a weak greedy baseline (supervised BQ greedy: 27.7% feasible) to 100% feasibility and 0.00% optimality gap at the top TaSaR inference budget (k=16, s=4) — it solves the test set. The LEHD group reaches the same destination (99.6% feasible, 0.32% gap on its robust Ours-only F* set). The headline metric here is feasibility, because — unlike TSP/CVRP/JSSP, where every decoded sequence is feasible by construction — Cloud Network Flow embeddings can and do fail capacity/chaining constraints, so feasibility is a real, primary metric under the lexicographic (feasibility-first, then gap) objective.

(2) Search scales quality to optimal (Phases 2–3). Increasing the inference compute budget — either deterministic beam width or the TaSaR (k,s) budget — improves feasibility and gap monotonically. Widening the deterministic beam from 1 to 64 lifts BQ feasibility 53.1%→99.2% and drops its gap 3.23%→1.75%, and LEHD 55.5%→99.6% with gap 3.78%→0.55% (Table 3). Crucially, at a matched node-transition budget the sample-and-reconsider decoder beats plain beam search: TaSaR(k=16, s=4) reaches gap ~0.07–0.32%, below the best deterministic beam-64 gaps — consistent with the paper's central claim that "take a step and reconsider" outperforms deterministic beam search. Greedy alone is comparatively weak throughout; the "reconsider" step is doing the heavy lifting.

(3) It generalizes far out of distribution (Phase 4). With no retraining, models trained on 60–80-node substrates stay strongly feasible on larger ones. At 1.35× scale, greedy feasibility drops (~53–56% → 44%, as expected for harder OOD instances) but beam-16 recovers it (BQ 87.5%, LEHD 100%). Pushing on unlabelled substrates, beam-16 feasibility holds ~75–87% out to 2.3× and remains ~50–56% at 4.6× the trained scale — while greedy collapses (12–50%). Again: search-based decoding is what carries generalization.

Two engineering enablers made this program tractable on modest hardware: a behaviour-preserving 8.6× speedup of TaSaR data generation (56s → 6.5s per 70-node instance), a lexicographic best-model selection fix ((1−feas)·1000 + gap, feasibility-first), and Gurobi wired in alongside HiGHS for ILP labelling at larger scales.

The one result most easily misread. The SIL step raises feasibility (Phase-1 seed ~37% → SIL ~53–63%) while the reported Gap%(F*) can rise slightly above the seed. This is not a quality regression. Gap% is averaged over F*, the set of instances feasible under every compared method; when SIL admits ~24pp of harder instances into the feasible pool, the gap is measured over a different, tougher subset (the feasible-pool-composition confound). Feasibility% (over the full N) is the clean, orderable headline metric; Gap%(F*) is deliberately conservative.

7.2 Limitations

The results are genuine but bounded. We flag the following honestly, so they are not over-read:

  • Architecture comparison is narrow. The BQ-vs-LEHD comparison is limited to the 128-width variants (BQ-128 / LEHD-128). Wider models (192 / 256) ran out of GPU memory on the available single-GPU hardware and were not evaluated, so we cannot speak to how the two architectures scale with capacity.
  • No non-neural baseline yet. There is no comparison against a heuristic or metaheuristic solver. Such solvers exist in the repo (vne_heuristic/: balanced-greedy and one-step-lookahead; vne_aco/: ant-colony optimization) but have not been run head-to-head against the learned policies. The current baselines are the supervised seed and the Gumbeldore/GD-SIL (un-truncated WOR-SBS, Top-p=1.0) run — and the latter diverged for the LEHD group, making it a failed rather than a fair baseline there.
  • Phase-4 gap evidence is thin. The out-of-distribution gap results (Table 4) rest on N=16 instances, a single seed, and reach only 1.35× scale. Moreover the 1.35× labels are time-bounded Gurobi solves (≤5% loose), whereas the 1× labels are exact — so the apparent gap improvement at larger scale is partly a label-tightness artifact, not a real quality gain. Only feasibility% (label-independent) extends robustly to ~4.6×, and even there N=16 per scale means the point values are noisy (read the trend, not individual cells).
  • No training-time k×s grid. The genuine-TaSaR runs fix the training search configuration (Top-p=0.9); we have not swept the training beam width / step size (k, s) grid to characterise how the SIL data-generation budget trades off against final policy quality. Inference-time scaling was studied; training-time scaling was not.
  • Timings are not paper-comparable. All wall-clock numbers are single-worker on one RTX 5060 (8 GB), whereas the TaSaR paper reports 4×RTX-3090 totals. Absolute ms/instance and set times here are illustrative of cost–quality shape, not comparable to the paper's throughput.
  • Reporting deviates from the paper by necessity. Feasibility% has no analogue in the paper's (always-feasible) domains, and Gap%(F*) is averaged over a fixed feasible-under-all denominator rather than the paper's whole-set average — so gap numbers are not directly comparable across the two works.

7.3 Future work

The most valuable next steps close the gaps above with comparatively cheap, evaluation-only or low-cost experiments:

  • Non-neural baselines. Run the existing vne_heuristic/ and vne_aco/ solvers on the same N=256 test set and OOD scales, and report them alongside the learned policies — this is the single most important missing comparison and requires no retraining.
  • Multi-seed error bars. Repeat the Phase-2 inference-scaling and the Phase-4 generalization measurements over ≥3 seeds to attach confidence intervals, and produce the deferred Feas%–vs–Gap% Pareto scatter. This directly addresses the N=16 / single-seed noise.
  • Larger-scale gap via more Gurobi capacity. The gap ceiling (1.35×) is a labelling bottleneck, not a model one — ILP solves explode with substrate size on one machine (≥120 nodes time out). Parallelising exact labelling across multiple Gurobi licenses would let the exact-optimum gap follow feasibility% out toward 2.3–4.6×.
  • Training k×s grid. Sweep the SIL data-generation search budget (beam width k and step size s, recalling that smaller s ⇒ more replan rounds ⇒ more compute) to map how training-time search intensity affects final policy feasibility/gap, complementing the inference-time scaling already established.
  • Wider architectures. Given multi-GPU memory, revisit BQ/LEHD at 192/256 width to characterise architecture scaling — LEHD's cleaner monotonic gap decrease (Phase 3) suggests it may benefit more from added capacity.
